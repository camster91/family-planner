# Family calling v1 — #612

Approved 2026-10-29: build voice and video family-device calls separately from PR #611.

UI/spec: use the existing rounded Dialog and semantic button styles. One **Call family** entry in the account menu and paired-board controls opens a named device picker. Each open tab is a distinct endpoint; paired screens use their canonical device label. The picker shows available/busy/DND. Incoming UI has Answer/Decline; active UI has Mute/End and an explicit Play audio fallback. No auto-answer or recording. Camera capture requires an explicit video-call action or Answer with video; answering a video call with voice downgrades both sides before negotiation. Voice calls never request a camera. Calling can be enabled by a parent with the existing family-feature controls. Each endpoint can turn availability off or enable DND. No new top-level tab.

Runtime: same canonical person/device identities and D1 household store. Authenticated, CSRF-protected session endpoints issue 60-second, purpose-bound grants, bound to the issuing session cookie and expected browser origin. Grants travel only in the WebSocket subprotocol, never URLs. The public Worker intercepts the socket path before the compute pool. A household-scoped Durable Object handles ephemeral endpoint presence, call state, and bounded WebRTC messages. Only its two admitted endpoints can signal a call. The object restores metadata from WebSocket attachments, never stores media/SDP/ICE in SQLite, and validates live identity/household/feature authority on actions and 15-second heartbeats. A stale/removed peer is disconnected; clients stop media on disconnect. No alarms, scheduler or background service is added.

Scope: one-to-one, specific-device voice/video calls while app pages are open. Video is capped at 720p/24fps and a 1.2 Mbps send target, with browser congestion control. First answer is unambiguous because calls target an endpoint. Ring timeout 30 seconds; active call limit 30 minutes. Simultaneous/busy calls, decline, cancel, network loss, permission refusal and audio-play restrictions have explicit UI states. Closed/suspended browsers are not promised incoming calls. Native push/CallKit/Android audio focus and account-wide multi-device fanout remain later work.

Rollout: `CALLING_ENABLED=1`, a configured `FAMILY_CALLS` binding and `CALLING_TURN_KEY_ID`/`CALLING_TURN_API_TOKEN` are required. The parent feature key `calling` defaults off for new and existing households. Existing permissions policy continues blocking microphones unless calling is deployed/enabled on a dashboard or shared-board page; camera/microphone remain blocked elsewhere. TURN master credentials stay server-side; authenticated session setup gets per-session short-lived ICE credentials. No provider, paid plan, secret or production flag is activated by implementing source. Missing configuration fails closed. Local fabricated fixtures may supply an explicitly development-only ICE configuration.

Acceptance: household isolation and current account/device revocation; original cookie/origin binding and expired/altered grants; bounded messages and busy/duplicate call transitions; microphone tracks stop on all end/unmount/error paths; two isolated browser endpoints establish an audio connection. Physical Safari/Android/tablet audio, Wi-Fi/mobile-data TURN and native background ringing remain separate acceptance gates. Do not infer these from fake-media browser checks.

References: Cloudflare DO WebSocket hibernation https://developers.cloudflare.com/durable-objects/best-practices/websockets/ and TURN credentials https://developers.cloudflare.com/realtime/turn/generate-credentials/.
